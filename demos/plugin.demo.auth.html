Themestrap · Plugin

Auth data-plugin-authjQuery only

Progressive enhancement for sign-in forms, with a pluggable network layer. Validation, password helpers and feedback work with any backend, and the adapter decides how the form talks to yours: MODX, a PHP session, Laravel, Django, a JWT API, Firebase or OAuth. Everything on this page runs against a fake backend inside the page.

Validation & Password Helpers

data-plugin-auth

The form layer needs no backend. Submit empty to see per-field errors, type a short password for minlength, type a different confirmation for data-auth-match, toggle the password, and watch the strength meter. Press Caps Lock while typing to see the hint.

Caps Lock is on 
<form data-plugin-auth data-auth-action="register">
    <div data-auth-field="password">
        <input name="password" type="password" required minlength="8" data-auth-strength data-auth-error>
        <button type="button" data-auth-toggle-password>Show</button>
        <div data-auth-strength-meter></div>
        <div data-auth-feedback></div>
    </div>
    <div data-auth-field="confirm">
        <input name="confirm" type="password" required data-auth-match="#password" data-auth-error>
        <div data-auth-feedback></div>
    </div>
</form>

The JSON Adapter and Reply Shapes

adapter: "json"

The same form against ten different server replies. Pick one and sign in: the plugin works out success, the message, field errors, tokens and redirects from whatever shape arrives. Note the HTML reply: a login page that answers with status 200 is never mistaken for success.

Caps Lock is on 
$('#login').themestrapPluginAuth({
    adapter:  'json',         // fetch, form-encoded, replies understood
    redirect: '/dashboard'    // same-origin only
});

// Or take over how a reply is read:
$('#login').themestrapPluginAuth({
    adapter:  'rest',
    response: { success: 'data.ok', token: 'data.jwt', message: (body) => body.data.text }
});

Two-step Sign-in (OTP)

data-auth-step

When the reply names a step ({"challenge": "code"}, or mfa_required for a step called otp), the plugin reveals it. Enter any username and an 8+ character password, then use the code 123456. A wrong code paints the field error from the server; the credentials are sent again with the code.

<div data-auth-step="credentials"> … username and password … </div>
<div data-auth-step="code">
    <div data-auth-field="code"> <input name="code" required data-auth-error> … </div>
</div>

// Server: { "challenge": "code" } reveals the step named "code".
// { "mfa_required": true } (or requires_otp) reveals a step named "otp".
// A name with no matching step changes nothing.
$('#login').on('auth:challenge', (e, auth, step) => console.log('now showing', step));

04

Your Own Adapter

registerAdapter()

Any backend that is not an HTTP form post: Firebase, Supabase, a WebAuthn ceremony, a local mock. An adapter is just submit(ctx) returning a result. This one pretends to be a client SDK. Use any email, and the password correct-horse.

themestrap.PluginAuth.registerAdapter('firebase', {
    submit: async function (ctx) {
        try {
            const cred = await firebase.auth().signInWithEmailAndPassword(ctx.data.email, ctx.data.password);
            return { ok: true, message: 'Signed in', token: await cred.user.getIdToken() };
        } catch (e) {
            return { ok: false, message: e.message };
        }
    }
});

05

Tokens for APIs

token.store · authHeaders()

For APIs that answer a sign-in with a token instead of a cookie. The token is kept in memory (or session or local storage), and PluginAuth.authHeaders() gives you the header for your own calls. Sign in, call the API, then sign out.

$('#login').themestrapPluginAuth({
    adapter: 'rest',          // JSON bodies
    csrf:    false,           // bearer APIs usually do not need it
    token:   { store: 'session' }
});

fetch('/api/me', { headers: themestrap.PluginAuth.authHeaders({ store: 'session' }) });

Lockout and Safe Redirects

retryAfter · ts.auth.redirect

The server answers every attempt with HTTP 429 and Retry-After: 8: the button locks with a live countdown. A separate form shows redirect safety: a reply pointing at another site is refused, and a successful redirect can be cancelled with preventDefault().

// Server: HTTP 429  +  Retry-After: 600   (or {"retryAfter": 600})
// The button shows "Try again in 9:58" and re-enables itself.

document.getElementById('login').addEventListener('ts.auth.redirect', (e) => {
    e.preventDefault();          // stay on the page; e.detail.url is the target
    router.go(e.detail.url);
});

07

OAuth and Social Providers

data-auth-provider

A button marked data-auth-provider starts a sign-in configured under providers, by full redirect or in a popup that reports back with postMessage. This demo redirects to a hash so you can see the click handled.

providers: {
    github: { url: '/auth/github' },                                     // full redirect
    google: { url: '/auth/google', mode: 'popup', width: 480, height: 640 }
}

// The popup page reports back:
window.opener.postMessage({ type: 'ts-auth', ok: true, redirect: '/app' }, location.origin);

Theming

--ts-au-*

Colours are custom properties with light, dark and explicit-light tiers, and the fallback styles use :where(), so Bootstrap wins when present and the form still looks right without it.

.warm-auth {
    --ts-au-invalid: #ff7a59;
    --ts-au-valid:   #ffd166;
    --ts-au-track:   rgba(255, 255, 255, .18);
}
